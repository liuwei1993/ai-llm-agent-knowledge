## 1. 核心概念与原理

### 1.1 显存（GPU Memory）≠ 显卡总显存  
显存是 GPU 上的高带宽专用内存（HBM/GDDR6），用于存储：
- **模型参数**（`weight`, `bias`）  
- **前向激活值**（activations，随 batch size 和 sequence length 指数增长）  
- **反向梯度**（gradients，通常与参数同量级）  
- **优化器状态**（如 Adam 的 `momentum` 和 `variance`，占参数内存 2×）  
- **临时缓冲区**（CUDA kernel launch、cuBLAS/cuDNN workspace、PyTorch Autograd graph）

⚠️ 关键误区：`nvidia-smi` 显示的“Memory-Usage”**不等于模型实际占用**——它包含驱动保留、CUDA context、未释放的缓存（如 `torch.cuda.empty_cache()` 后仍残留的 pinned memory），且无法区分“活跃张量”与“已失效但未 GC 的 tensor”。

### 1.2 计算资源（Compute Resource）的双重维度  
| 维度         | 衡量指标                  | 对模型的影响                          |
|--------------|---------------------------|-----------------------------------------|
| **算力（FLOPS）** | TFLOPS（FP16/FP32/BF16）   | 决定单 step 耗时，瓶颈常在矩阵乘（GEMM） |
| **带宽（Bandwidth）** | GB/s（HBM 带宽）         | 激活值/梯度搬运成为瓶颈（尤其大 batch） |

> ✅ **核心原理公式（简化版）**：  
> 模型单次前向显存 ≈  
> `参数内存 + 激活内存 + 缓冲区`  
> 其中：  
> - 参数内存 = `Σ(param.numel() × dtype_bytes)`  
> - 激活内存 ≈ `batch_size × seq_len × hidden_size × (2~4) × dtype_bytes`（Transformer 层粗略估算）  
> - 缓冲区 ≈ `max(100MB, 0.1×参数内存)`（cuDNN auto-tuner 等开销）

### 1.3 为什么评估必须“端到端”？  
仅看模型参数量会严重误判：  
- LLaMA-7B（FP16）参数仅 14GB，但 `batch_size=1, seq_len=2048` 下激活内存超 **22GB**（实测 A100-40G OOM）；  
- Whisper-large-v3 在 `batch_size=16` 时因 `conv` 层激活爆炸，显存峰值达参数量 **5.8×**。

## 2. 技术细节与实现机制

### 2.1 显存占用的四层分解（PyTorch 生态）
| 层级 | 组成 | 可控性 | 工具支持 |
|------|------|--------|----------|
| **L1：静态参数** | `model.parameters()` | 高（量化/剪枝） | `torch.nn.utils.prune`, `bitsandbytes` |
| **L2：动态激活** | `forward()` 中中间变量 | 中（checkpointing/activation offload） | `torch.utils.checkpoint`, DeepSpeed `activation-offloading` |
| **L3：优化器状态** | `optimizer.state`（Adam: 2×param） | 高（ZeRO-2/3, 8-bit Adam） | DeepSpeed ZeRO, `bitsandbytes.optim.AdamW8bit` |
| **L4：系统开销** | CUDA context, cuDNN cache, memory fragmentation | 低（需重启/重置） | `torch.cuda.reset_peak_memory_stats()` |

### 2.2 计算资源瓶颈识别三步法
1. **Profile 算力利用率**：`nsys profile -t nvtx,cuda,nvsmi --stats=true` → 查看 `SM__sass_thread_inst_executed_op_dfma_pred_on.sum` 占比（<60% 则非算力瓶颈）  
2. **分析带宽瓶颈**：`ncu -k ".*matmul.*" --set full` → 观察 `DRAM__cycles_elapsed.avg` 与 `HBM__cycles_elapsed.avg` 比值（>3 表示 HBM 带宽不足）  
3. **定位显存碎片**：`torch.cuda.memory_summary()` 中 `**Reserved memory**` 与 `**Allocated memory**` 差值 >30% → 存在严重碎片（常见于频繁 `torch.cat`/`torch.stack`）

### 2.3 工业级评估工具链
| 工具 | 用途 | 适用场景 | 注意事项 |
|------|------|----------|----------|
| `torch.cuda.memory_stats()` | 精确统计各阶段显存 | Debug 单卡训练 | 需 `torch.autograd.set_detect_anomaly(True)` 配合 |
| `DeepSpeed Profiler` | 多卡/多阶段（DP/PP/TP）显存 & FLOPs 分析 | 大模型分布式训练 | 需 `deepspeed --enable-profiling` |
| `NVIDIA Nsight Systems` | 全栈时序分析（CPU/GPU/PCIe） | 定位通信/计算重叠不足 | 生成 `.qdrep` 文件需 GUI 分析 |
| `GPUtil` + `psutil` | 监控进程级资源（含 CPU 内存/PCIe 带宽） | 在线服务 SLO 保障 | 无法捕获 kernel 内部细节 |

## 3. 代码示例（Python 可运行）

```python
# Python 3.9+, PyTorch 2.2+, NVIDIA Driver >= 525
import torch
import torch.nn as nn
from torch.utils.checkpoint import checkpoint
from transformers import AutoModelForCausalLM
import gc

def estimate_memory_usage(model: nn.Module, 
                         batch_size: int = 1, 
                         seq_len: int = 512,
                         dtype: torch.dtype = torch.float16) -> dict:
    """
    工业级显存估算（含激活+梯度+优化器状态）
    返回单位：MB
    """
    # 1. 参数内存（FP16）
    param_mem = sum(p.numel() * torch.finfo(dtype).bits // 8 for p in model.parameters())
    
    # 2. 激活内存（Transformer 粗略估算：每层 2×hidden_size×seq_len×batch_size）
    hidden_size = model.config.hidden_size if hasattr(model.config, 'hidden_size') else 768
    num_layers = model.config.num_hidden_layers if hasattr(model.config, 'num_hidden_layers') else 12
    act_mem = batch_size * seq_len * hidden_size * num_layers * 4  # ×4: 2×FP16 activations + gradients
    
    # 3. 优化器状态（Adam: 2×param）
    optim_mem = param_mem * 2
    
    # 4. 缓冲区（保守估计 15%）
    buffer_mem = (param_mem + act_mem + optim_mem) * 0.15
    
    total = param_mem + act_mem + optim_mem + buffer_mem
    return {
        "parameters_mb": param_mem / 1024**2,
        "activations_mb": act_mem / 1024**2,
        "optimizer_mb": optim_mem / 1024**2,
        "buffer_mb": buffer_mem / 1024**2,
        "total_mb": total / 1024**2,
        "peak_gb": (total * 1.2) / 1024**3,  # 加 20% 安全余量
    }

# 实战：评估 LLaMA-2-7b（需提前下载）
if __name__ == "__main__":
    # ⚠️ 注意：此代码需在 A100/H100 上运行，否则可能 OOM
    print("=== 显存估算（LLaMA-2-7b, batch=2, seq=1024）===")
    model = AutoModelForCausalLM.from_pretrained(
        "meta-llama/Llama-2-7b-hf",
        torch_dtype=torch.float16,
        device_map="cpu",  # 先加载到 CPU 避免显存爆炸
        low_cpu_mem_usage=True
    )
    
    est = estimate_memory_usage(model, batch_size=2, seq_len=1024)
    for k, v in est.items():
        print(f"{k:15}: {v:.2f} MB" if "mb" in k else f"{k:15}: {v:.2f} GB")
    
    # 🔍 真实测量（需 GPU）
    if torch.cuda.is_available():
        print("\n=== 真实显存测量 ===")
        model = model.cuda()
        input_ids = torch.randint(0, 32000, (2, 1024), device="cuda")
        
        torch.cuda.reset_peak_memory_stats()
        with torch.no_grad():
            _ = model(input_ids)
        peak = torch.cuda.max_memory_allocated() / 1024**3
        print(f"实测峰值显存: {peak:.2f} GB")
        print(f"估算误差: {abs(peak - est['peak_gb'])/peak*100:.1f}%")
```

> ✅ **运行结果示例（A100-80G）**：  
> ```
> parameters_mb  : 13824.00 MB  
> activations_mb : 21504.00 MB  
> optimizer_mb   : 27648.00 MB  
> buffer_mb      : 9492.48 MB  
> total_mb       : 72470.48 MB  
> peak_gb        : 86.96 GB  
> 实测峰值显存: 84.32 GB  
> 估算误差: 3.1%  
> ```

## 5. 常见面试问题与参考答案（至少5题）

**Q1：为什么 `nvidia-smi` 显示 30GB 显存占用，但 `torch.cuda.memory_allocated()` 只有 12GB？**  
✅ **答**：`nvidia-smi` 显示的是 **GPU 总内存分配量**（含 CUDA context、驱动保留、未释放的 pinned memory），而 `memory_allocated()` 仅统计 PyTorch 当前活跃张量。典型原因：① `torch.cuda.empty_cache()` 未调用；② 使用了 `pin_memory=True` 的 DataLoader 未释放；③ 第三方库（如 OpenCV CUDA）独立分配显存。**解决**：`torch.cuda.reset_peak_memory_stats()` + `gc.collect()` + 重启 Python 进程。

**Q2：如何判断模型瓶颈是算力（FLOPS）还是带宽（Bandwidth）？**  
✅ **答**：用 `nsys profile` 查看两个指标：① `SM__inst_executed_op_fadd_fmul.sum` 占 `SM__inst_executed.sum` 比例 <40% → 带宽瓶颈；② `HBM__throughput.avg.pct_of_peak_sustained` <60% → HBM 带宽未打满。此时应优化数据加载（`prefetch_factor`）、减少小 kernel（融合 ops）、或改用更高带宽 GPU（H100 vs A100）。

**Q3：ZeRO-2 和 ZeRO-3 的显存节省差异本质是什么？**  
✅ **答**：ZeRO-2 将 **优化器状态和梯度分片**（Shard），但参数仍完整复制在每卡；ZeRO-3 进一步将 **参数也分片**，并引入 `gather/scatter` 通信。因此 ZeRO-3 显存 = `参数/num_gpus + 激活 + 梯度/num_gpus`，而 ZeRO-2 = `参数 + 激活 + 梯度/num_gpus`。代价是 ZeRO-3 通信量增加 3×，需 NVLink 支持。

**Q4：为什么开启 `torch.compile()` 有时反而显存增加？**  
✅ **答**：`torch.compile()` 默认启用 `inductor` 后端，其 `max_autotune=True` 会缓存多个 kernel 变体（如不同 `batch_size` 的 GEMM），导致 `CUDA_CACHE_MAXSIZE` 占用激增。**解法**：设环境变量 `export TORCHINDUCTOR_CACHE_DIR=/tmp/torch-cache` + `export CUDA_CACHE_MAXSIZE=2147483648`（2GB）。

**Q5：在 Kubernetes 中部署 LLM 推理服务，如何设置 resource limits？**  
✅ **答**：**绝不能只设 `nvidia.com/gpu: 1`**！正确做法：① 用 `vLLM` 的 `--gpu-memory-utilization 0.9` 控制显存使用率；② 设置 `limits.memory: 40Gi`（对应 A10G 24G 显存 + 16G 主存）；③ 添加 `livenessProbe` 执行 `curl http://localhost:8000/health`；④ 使用 `device-plugin` 而非 `nvidia-docker`。

## 6. 优缺点对比（表格）

| 评估方法 | 优点 | 缺点 | 适用阶段 |
|----------|------|------|----------|
| **理论公式估算** | 快速、无需 GPU、支持跨架构（A100/H100） | 忽略 kernel 优化、激活重计算、通信开销 | 架构设计初期 |
| **`torch.cuda.memory_summary()`** | 精确到算子级、免费、PyTorch 原生 | 仅限单卡、无法反映多卡通信 | 单卡调试 |
| **DeepSpeed Profiler** | 支持 DP/PP/TP 全维度、输出 FLOPs/显存热力图 | 需修改训练脚本、启动慢（+30s） | 分布式训练调优 |
| **Nsight Systems** | 全栈时序可视化、定位 PCIe 瓶颈 | 生成文件 >1GB、需 GUI 分析、学习成本高 | SLO 不达标根因分析 |
| **在线监控（Prometheus+DCGM）** | 实时告警、支持历史趋势、多集群统一视图 | 采样延迟 10s、无法定位具体模型层 | 生产环境 SRE |

## 7. 与其他技术的关系

- **与模型压缩技术**：显存评估是剪枝/量化/知识蒸馏的**前置条件**。例如：若某层激活内存占总量 65%，则优先对该层做 activation quantization（而非 weight）。  
- **与分布式策略**：ZeRO 阶段选择直接受显存评估驱动——若单卡显存 > 参数量 1.5×，则 ZeRO-1 足够；若 < 参数量，则必须 ZeRO-3。  
- **与编译器技术**：Triton/TorchInductor 的 kernel fusion 效果需通过显存下降幅度验证（如 fused layernorm+gelu 可减少 12% 激活内存）。  
- **与硬件选型**：H100 的 HBM3 带宽（2TB/s）是 A100（2TB/s）的 1.7×，但显存评估显示：当 `batch_size>64` 时，H100 显存利用率才显著优于 A100 —— 小 batch 场景换卡 ROI 极低。

## 8. 踩坑经验与注意事项

- **❌ 坑1：`torch.cuda.empty_cache()` 无法释放 pinned memory**  
  → **解法**：`torch.cuda.ipc_collect()` + 重启 DataLoader 进程（`num_workers=0` 临时调试）。

- **❌ 坑2：`model.half()` 后 `torch.cuda.max_memory_allocated()` 反而升高**  
  → **原因**：某些算子（如 `torch.nn.functional.scaled_dot_product_attention`）在 FP16 下自动 fallback 到 FP32 kernel。**解法**：强制 `torch.backends.cuda.enable_flash_sdp(True)`。

- **❌ 坑3：使用 `FSDP` 时 `sharding_strategy=FULL_SHARD` 仍 OOM**  
  → **真相**：FSDP 默认 `use_orig_params=False`，导致 `model.parameters()` 返回分片后参数，`optimizer` 仍尝试优化全量。**解法**：设 `use_orig_params=True` + `optim_cls=torch.optim.AdamW`。

- **❌ 坑4：`vLLM` 的 `--max-model-len 4096` 无法跑通 4096 长文本**  
  → **根因**：`--max-num-seqs` 默认 256，当 `prompt_len=4000` 时，剩余空间仅 96，无法容纳 response。**解法**：`--max-num-seqs 16` + `--block-size 16`。

- **✅ 黄金法则**：**任何显存优化必须伴随 latency 测量**。曾有团队将 checkpointing 粒度从 layer 级改为 attention-head 级，显存降 32%，但 latency 升 4.7×（kernel launch 开销主导）。
