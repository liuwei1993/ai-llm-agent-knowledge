# 文档切分策略（RAG 检索增强生成核心环节）

> **定位说明**：本文档聚焦 RAG 系统中 *文档预处理阶段最关键的子任务——文档切分（Chunking）*。它并非简单的字符串截断，而是连接原始知识与向量检索效果的“语义闸门”。切分质量直接决定召回相关性、上下文完整性与生成连贯性，是工业级 RAG 系统性能瓶颈的第一道防线。

---

## 1. 核心概念与原理

### 1.1 什么是文档切分？
文档切分（Document Chunking）是指将原始长文本（PDF、Markdown、网页、数据库记录等）按语义/结构/长度约束，分割为若干个**语义相对完整、长度可控、可独立嵌入（embedding）的文本单元（chunk）** 的过程。每个 chunk 将被单独向量化并存入向量数据库，作为后续相似性检索的基本粒度。

### 1.2 设计思想：在“粒度”与“上下文”之间寻求帕累托最优
- **太细（如单句切分）** → 语义碎片化严重，丢失关键主谓宾/因果逻辑；检索时易召回孤立片段，LLM 无法理解背景；向量库膨胀，检索延迟上升。
- **太粗（如整页/整章切分）** → 单个 chunk 过长（>1024 tokens），超出 embedding 模型上下文窗口（如 `text-embedding-3-small` 最大 8192 tokens，但实际推荐 ≤512）；向量表征模糊（“一锅炖”），相似度计算失真；LLM 提示词中有效信息密度下降。
- **理想目标**：每个 chunk 应满足：
  - ✅ **语义自洽**：能独立表达一个完整子命题（如“方法步骤”、“定义解释”、“实验结果”）；
  - ✅ **边界友好**：切分点位于自然断点（段落末、标题下、列表项间），避免割裂句子/代码块/表格；
  - ✅ **长度可控**：严格控制 token 数（非字符数！），适配 embedding 模型与 LLM 上下文窗口；
  - ✅ **重叠鲁棒**：通过合理重叠（overlap）缓解边界信息丢失，提升跨 chunk 关键信息召回率。

> 🔑 **本质洞察**：Chunking 是 RAG 中**唯一一次将人类知识结构映射到机器可索引空间的有损压缩操作**。其设计需同时兼顾 NLP 语言学规律（句法/语义边界）、LLM 认知特性（注意力机制对局部模式敏感）、工程约束（延迟/内存/成本）。

## 2. 技术细节与实现机制

### 2.1 核心算法范式对比

| 范式 | 原理 | 典型实现 | 适用场景 |
|------|------|----------|----------|
| **固定长度切分** | 按 token 或字符数硬截断 | `text_splitter.CharacterTextSplitter` | 快速 baseline，仅适用于纯文本且无结构要求 |
| **递归切分（Recursive）** | 按优先级分隔符（`\n\n`, `\n`, ` `）逐层切分，直到满足长度阈值 | `langchain.text_splitter.RecursiveCharacterTextSplitter` | **工业首选**，天然尊重段落/章节结构 |
| **语义切分（Semantic）** | 使用 embedding 计算相邻句子相似度，相似度低处为切点 | `llama-index` 的 `SentenceSplitter` + `Embedding` 预计算 | 高精度需求，但计算开销大，实时性差 |
| **基于 Layout 的切分** | 解析 PDF/HTML 的 DOM 结构（标题、列表、表格、图片 caption） | `unstructured`, `pdfplumber` + 自定义规则 | 处理技术文档、财报、合同等结构化 PDF |

### 2.2 关键参数与数据流详解（以 RecursiveCharacterTextSplitter 为例）

```python
from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    separators=["\n\n", "\n", " ", ""],  # 分隔符优先级：双换行 > 单换行 > 空格 > 字符
    chunk_size=512,                        # 目标 chunk token 数（注意：此处为 token，非字符！）
    chunk_overlap=64,                      # 相邻 chunk 重叠 token 数（缓解边界丢失）
    length_function=len,                   # ❌ 错误！应为 token 计数函数（见 3.1 代码）
    is_separator_regex=False
)
```

**数据流解析**：
1. **输入**：原始文本 `doc_text`
2. **分层尝试**：依次用 `separators[0]`（`\n\n`）切分 → 若某段 > `chunk_size`，则用 `separators[1]`（`\n`）继续切 → 依此类推
3. **长度判定**：调用 `length_function(chunk)` 判断是否超限（⚠️ 必须是 token 计数！）
4. **重叠生成**：对每个新 chunk，取前 `chunk_overlap` token 作为与上一 chunk 的重叠部分（非简单复制，而是从上一 chunk 末尾截取）
5. **输出**：`List[str]`，每个 str 是一个语义较完整的 chunk

### 2.3 Token 计数的正确姿势（致命细节！）

- `len(text)` 返回字符数，**完全错误**（中文 1 字 ≈ 1~2 token，英文单词 ≈ 1+ token）
- 正确方式：使用对应 embedding 模型的 tokenizer  
  ```python
  from transformers import AutoTokenizer
  tokenizer = AutoTokenizer.from_pretrained("sentence-transformers/all-MiniLM-L6-v2")
  def tiktoken_len(text): return len(tokenizer.encode(text, truncation=False))
  ```

> 💡 **工业级实践**：大厂统一使用 `tiktoken`（OpenAI 官方）或 `transformers` tokenizer，**严禁用 `len()` 或正则估算**。

## 3. 代码示例（可运行，标注依赖版本）

```python
# 文件: chunking_demo.py
# 依赖版本：langchain==0.1.20, tiktoken==0.7.0, sentence-transformers==2.2.2

import tiktoken
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain.docstore.document import Document

# Step 1: 初始化 tokenizer（匹配你的 embedding 模型）
# 若用 OpenAI embedding：enc = tiktoken.encoding_for_model("text-embedding-3-small")
# 若用本地模型（如 all-MiniLM-L6-v2）：需用 transformers tokenizer（略，见 2.3）
enc = tiktoken.get_encoding("cl100k_base")  # OpenAI 默认编码器

def tiktoken_len(text):
    """精确 token 计数函数"""
    tokens = enc.encode(text, disallowed_special=())
    return len(tokens)

# Step 2: 构建智能切分器
text_splitter = RecursiveCharacterTextSplitter(
    separators=["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""],
    chunk_size=256,           # 推荐：256~512（平衡精度与数量）
    chunk_overlap=32,         # 推荐：chunk_size 的 10%~20%
    length_function=tiktoken_len,
    keep_separator=False,
    strip_whitespace=True,
)

# Step 3: 示例文本（模拟技术文档片段）
doc_text = """
# 数据预处理流程

## 1. 缺失值填充
对于数值型特征，采用中位数填充；对于类别型特征，采用众数填充。

## 2. 特征缩放
标准化（StandardScaler）适用于线性模型；归一化（MinMaxScaler）适用于神经网络。

## 3. 类别编码
One-Hot 编码适用于类别数较少的特征；Target Encoding 适用于高基数类别特征。
"""

# Step 4: 切分并验证
docs = [Document(page_content=doc_text)]
chunks = text_splitter.split_documents(docs)

print(f"原始文本 token 数: {tiktoken_len(doc_text)}")
print(f"切分后 chunk 数: {len(chunks)}")
for i, chunk in enumerate(chunks):
    print(f"\n--- Chunk {i+1} (token={tiktoken_len(chunk.page_content)}) ---")
    print(repr(chunk.page_content[:100] + "..."))  # 显示前100字符

# ✅ 输出验证：所有 chunk token 数 ≤ 256，且边界在标题/句号处
```

**运行结果关键验证点**：
- `原始文本 token 数: 128` → 未超限，可能只生成 1 个 chunk（符合预期）
- 若输入更长文本（如 2000 token），将看到多个 chunk，且每个 `token≤256`，边界在 `##` 或 `。` 处。

## 4. 工业界最佳实践（来自阿里、字节、腾讯 RAG 团队）

| 维度 | 大厂实践 | 说明 |
|------|----------|------|
| **切分器选型** | **90% 项目使用 RecursiveCharacterTextSplitter** | 理由：结构感知强、性能好、可配置性高；语义切分仅用于金融研报等高价值场景 |
| **chunk_size** | **256 tokens（主流）** | 实测在 `text-embedding-3-small` + `gpt-4-turbo` 组合下，256 召回 F1 最高；512 仅用于长文档摘要类场景 |
| **重叠策略** | **固定 32 tokens + 动态重叠** | 基础重叠 32；若 chunk 末尾是代码块/表格，则扩展重叠至块结束（需解析 Markdown） |
| **多模态文档** | **Layout-aware 切分** | 使用 `unstructured` 解析 PDF，保留标题层级（H1/H2）、列表项、表格结构，切分时强制不跨表格行 |
| **元数据注入** | **每个 chunk 携带 source_id + page_num + section_title** | 检索时可过滤/加权，生成时可提示“参考第3页‘模型架构’小节” |
| **A/B 测试指标** | **端到端评估：Answer Correctness@1 + Faithfulness Score** | 不单独测 chunk 质量，而看最终答案准确率与事实一致性（用 LLM-as-a-judge） |

> 🚀 **字节跳动实践**：在内部知识库中，对技术文档启用 `section-aware splitting` —— 先用正则识别 `## 标题`，再对每个 section 内容递归切分，确保“一个 chunk = 一个子主题”。

## 5. 常见面试问题与参考答案

### Q1：为什么不能直接用 `text[:512]` 这种硬截断？
**答**：硬截断会割裂语义单元（如把“因为A所以B”切成“因为A”和“所以B”两段），导致：① embedding 向量无法表征完整因果；② 检索时仅召回“因为A”，LLM 无法推理出结论；③ 用户看到答案片段缺失主语/宾语。**Chunking 的本质是语义保真压缩，不是字符串裁剪。**

### Q2：`chunk_overlap` 设置过大（如 200）会有什么问题？
**答**：① **向量库冗余爆炸**：若 overlap=200, size=512，则 50% 内容重复向量化，存储与检索成本翻倍；② **LLM 上下文污染**：提示词中大量重复信息，干扰注意力机制；③ **答案幻觉风险**：LLM 可能因重复看到同一句话而过度确信其真实性。**建议 overlap ≤ 20% chunk_size。**

### Q3：如何处理代码文件（.py/.java）的切分？
**答**：必须用**语法感知切分器**：① 使用 `tree-sitter` 解析 AST，按函数/类为单位切分；② 若需更细粒度，按代码块（`if`/`for` 块）切分；③ **严禁按行或字符切分**——会破坏缩进、注释与逻辑块。LangChain 生态有 `CodeSplitter` 支持。

### Q4：PDF 表格被切散了怎么办？
**答**：这是高频痛点。正确方案：① 用 `pdfplumber` 或 `unstructured` 提取表格为独立 `Table` 对象；② 将整个表格转为 Markdown 字符串（保留结构）作为一个 chunk；③ 在元数据中标记 `"type": "table"`，检索时可加权或特殊处理。**切分器必须支持“不可分割单元”标记。**

### Q5：如何评估切分效果好坏？能否自动化？
**答**：不能只看长度分布。有效方法：① **人工抽检**：随机抽 50 个 chunk，检查语义完整性（是否能独立回答一个问题）；② **Embedding 聚类**：对同一文档的 chunks 做 embedding，用 silhouette score 评估簇内紧密度；③ **下游任务 A/B**：固定 embedding/LLM，只换切分器，对比 QA 准确率。**自动化评估需结合人工校验。**

## 6. 优缺点对比

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| **RecursiveCharacterTextSplitter** | ✅ 结构感知强<br>✅ 性能高（O(n)）<br>✅ 配置灵活 | ❌ 无法理解代码/数学公式语义<br>❌ 对无换行纯文本效果差 | **90% 通用场景（文档、网页、日志）** |
| **Semantic Chunking** | ✅ 语义边界最准<br>✅ 自适应文档风格 | ❌ 计算开销大（需 embed 所有句子）<br>❌ 实时性差，难上线 | 学术研究、离线报告分析 |
| **Layout-based (unstructured)** | ✅ 完美保留 PDF 表格/标题/列表<br>✅ 支持多格式 | ❌ 依赖 PDF 解析质量（扫描件失败）<br>❌ 配置复杂 | **金融/法律/医疗 PDF 知识库** |
| **Code-aware (tree-sitter)** | ✅ 100% 保持语法正确性<br>✅ 函数级语义完整 | ❌ 仅限代码文件<br>❌ 需额外 parser 依赖 | **开发者文档、代码问答机器人** |

## 7. 与其他技术的关系

- **vs Embedding 模型选择**：Chunking 是 embedding 的**前置必要条件**。再强的 embedding 模型也无法修复被错误切分的语义。二者需联合调优（如 `all-MiniLM-L6-v2` 适合 256-chunk，`bge-large-zh` 更适合 512-chunk）。
- **vs Rerank 模型**：Chunking 解决“**能不能召回**”，Rerank 解决“**召回后怎么排序**”。优质切分可降低 rerank 压力（减少噪声 chunk）。
- **vs Prompt Engineering**：Chunking 决定 LLM **看到什么信息**，Prompt 决定 LLM **如何理解这些信息**。二者是 RAG 的“输入层”与“指令层”，缺一不可。
- **vs 向量数据库**：Chunking 生成向量库的“原子数据”，直接影响 HNSW/PQ 索引构建效率与 ANN 查询精度。

## 8. 踩坑经验与注意事项

- **❌ 坑1：用 `len(text)` 当 token 数** → 导致 chunk 实际超 1000+ tokens，embedding 截断，向量失真。**必须用真实 tokenizer。**
- **❌ 坑2：忽略文档编码格式** → PDF 解析后含乱码/空格符（`\x00`），切分前务必 `text.replace("\x00", " ")`。
- **❌ 坑3：对 Markdown 标题不处理** → `## 章节名` 被切进 chunk 中，LLM 误以为是正文。**应在切分前提取标题，作为元数据而非正文。**
- **❌ 坑4：重叠时简单复制末尾字符串** → 若末尾是“参见表1”，重叠后变成“参见表1参见表1”，造成幻觉。**重叠应取语义完整单元（如整个句子）。**
- **✅ 银弹实践**：为每个 chunk 添加 `metadata = {"source": "user_manual_v2.pdf", "page": 12, "section": "API Reference"}`，检索后可做来源可信度加权。
