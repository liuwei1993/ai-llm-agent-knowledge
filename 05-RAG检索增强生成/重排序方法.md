# 重排序方法（Reranking in RAG）

> **定位说明**：本文档聚焦于 RAG（Retrieval-Augmented Generation）系统中**检索后阶段的关键优化技术——重排序（Reranking）**。它并非替代传统向量检索，而是对初检结果进行语义精细化打分与重排，显著提升 Top-K 相关文档质量，是工业级 RAG 系统落地的“精度放大器”。面向具备 1–2 年 LLM/搜索/AI 工程经验的开发者，强调原理深度、工程权衡与真实场景陷阱。

---

## 1. 核心概念与原理

### 1.1 什么是重排序（Reranking）？
重排序是指：在**向量数据库初检（如 FAISS/Annoy/Pinecone 返回 top-100 候选）之后**，使用更强大但计算开销更高的模型，对这组候选文档（通常 10–100 条）进行**细粒度语义相关性打分**，并依据新分数重新排序，最终截取 top-K（如 K=5）作为生成器输入的过程。

> ✅ **本质**：一种“两阶段检索”（Two-Stage Retrieval）中的第二阶段 —— **用高精度换低吞吐，以可控成本换取显著效果提升**。

### 1.2 设计思想：精度-效率的帕累托最优
- **第一阶段（粗排）**：用轻量级稠密向量（如 `text-embedding-3-small`）做 ANN 检索，保障毫秒级响应与百万级召回能力；
- **第二阶段（重排）**：用上下文感知更强、参数量更大、支持 query-doc 交互建模的模型（如 Cross-Encoder），对小批量候选做**联合编码（joint encoding）**，捕捉 query 与 doc 的深层语义匹配信号（如指代消解、逻辑蕴含、否定识别等）。

> 🔑 关键洞见：  
> 向量检索本质是“单塔”（single-tower）表征匹配，仅依赖独立编码的 embedding cosine similarity；而重排序采用“双塔+交互”或纯“交叉编码”（cross-encoding），显式建模 query-doc 对的语义对齐关系 —— 这正是其精度跃升的根本原因。

### 1.3 为什么 RAG 必须重排序？
| 问题场景 | 向量检索失效原因 | 重排序如何修复 |
|----------|------------------|----------------|
| **Query 表达模糊**（如 “苹果怎么吃？”） | embedding 无法区分“水果” vs “公司”，初检混入无关科技新闻 | Cross-encoder 在 query-doc pair 上联合推理，结合上下文判别实体歧义 |
| **长尾/专业术语**（如 “CRISPR-Cas9 脱靶效应检测方法”） | 小样本微调 embedding 缺乏领域泛化力，相似度计算失准 | 重排模型可基于公开领域数据（如 PubMedBERT）微调，强化生物医学语义理解 |
| **文档结构噪声**（PDF 解析后含页眉/表格/乱码） | 向量 embedding 被噪声稀释，关键段落权重降低 | 重排模型通过 attention 机制自动聚焦 query 相关句子（如 [CLS] token score 可视化验证） |

> 💡 **一句话总结**：重排序不是“锦上添花”，而是 RAG 从“能跑通”迈向“生产可用”的**必要精度校准环节** —— 尤其当你的 RAG 服务于金融研报摘要、医疗问答、法律条款引用等高置信度场景时。

## 2. 技术细节与实现机制

### 2.1 主流重排序架构分类

| 类型 | 代表模型 | 输入形式 | 计算复杂度 | 特点 |
|------|-----------|-----------|-------------|------|
| **Cross-Encoder** | `bge-reranker-base`, `cross-encoder/ms-marco-MiniLM-L-6-v2` | `[CLS] query [SEP] doc [SEP]` 单序列输入 | O(L²)（L 为总 token 长度） | 最高精度；必须 batch inference；不可缓存 doc embedding |
| **Bi-Encoder + Interaction Head** | `cohere-rerank-v3`, `jina-reranker-v2` | query embedding + doc embedding → MLP/Attention 交互 | O(d)（d 为 embedding 维度） | 支持预计算 doc embedding；精度略低于 Cross-Encoder；延迟更低 |
| **LLM-as-a-Reranker** | 使用 Llama-3-8B 或 Qwen2-7B，prompt: `"Rate relevance [1-5]: Query: {q} Doc: {d}"` | Text prompt + LLM generation | O(N×L×d)（N 为候选数） | 零样本强泛化；但成本高、不稳定；需 careful prompt engineering |

> 📌 **工业首选：Cross-Encoder** —— 因其在 MS-MARCO、BEIR 等权威 benchmark 上持续 SOTA，且开源生态成熟（HuggingFace Transformers + SentenceTransformers）。

### 2.2 Cross-Encoder 工作流程（以 `BAAI/bge-reranker-base` 为例）

```mermaid
graph LR
A[User Query] --> B[Vector DB 初检]
B --> C[Top-100 candidate docs]
C --> D[Batched Input Construction]
D --> E["Tokenize: <s>query</s><s>doc_i</s>"]
E --> F[RoBERTa-based Cross-Encoder]
F --> G[Output: logits[0] = relevance score]
G --> H[Sort by score → select top-5]
H --> I[Feed to LLM Generator]
```

- **关键机制**：
  - 使用 `<s>` / `</s>` 作为特殊分隔符（非 `[CLS]/[SEP]`），适配 BGE 系列 tokenizer；
  - 模型输出为单个 scalar（logits[0]），经 sigmoid 映射为 [0,1] 相关性概率；
  - **不训练 decoder**，仅用 encoder 的 pooled output → 全连接层 → sigmoid；
  - 支持 FP16 推理 + dynamic batching（HuggingFace `pipeline` 自动优化）。

### 2.3 数据流与延迟瓶颈分析

| 阶段 | 典型耗时（CPU/GPU） | 瓶颈来源 | 优化手段 |
|------|---------------------|-----------|------------|
| Tokenization | 2–5 ms / doc | Python 字符串处理 + tokenizer lookup | 使用 `tokenizers` 库预编译 tokenizer；batch encode |
| Model Forward | 8–25 ms / doc（A10G） | Transformer self-attention（O(L²)） | TensorRT-LLM 编译；FlashAttention-2；KV cache 复用（仅限 batch 内） |
| Score Post-process | <0.5 ms | NumPy sort | `np.argpartition` 替代 full sort（仅需 top-K） |

> ⚠️ 注意：重排序延迟 ≈ `batch_size × per_doc_latency`，因此 **batch size 是核心调优参数**（通常设为 16–32）。过大导致显存 OOM；过小则 GPU 利用率低下。

## 3. 代码示例（可运行 · PyTorch 2.3 + Transformers 4.41）

```python
# file: reranker_demo.py
# pip install torch==2.3.0 transformers==4.41.0 sentence-transformers==3.0.0 accelerate==0.30.1

from typing import List, Tuple, Dict, Optional
import torch
from transformers import AutoTokenizer, AutoModelForSequenceClassification
from sentence_transformers import util
import numpy as np

class CrossEncoderReranker:
    def __init__(
        self,
        model_name: str = "BAAI/bge-reranker-base",
        device: str = "cuda" if torch.cuda.is_available() else "cpu",
        max_length: int = 512,
        batch_size: int = 16,
    ):
        self.tokenizer = AutoTokenizer.from_pretrained(model_name)
        self.model = AutoModelForSequenceClassification.from_pretrained(model_name).to(device)
        self.model.eval()
        self.device = device
        self.max_length = max_length
        self.batch_size = batch_size

    def _prepare_batch(self, query: str, docs: List[str]) -> Dict:
        """Construct [CLS]query[SEP]doc[SEP] inputs"""
        pairs = [[query, doc] for doc in docs]
        features = self.tokenizer(
            pairs,
            padding=True,
            truncation=True,
            max_length=self.max_length,
            return_tensors="pt",
        )
        return {k: v.to(self.device) for k, v in features.items()}

    @torch.no_grad()
    def rerank(
        self, query: str, docs: List[str], top_k: int = 5
    ) -> List[Tuple[str, float]]:
        """
        Rerank docs by relevance score. Returns [(doc, score), ...] sorted descending.
        """
        scores = []
        # Process in batches to avoid OOM
        for i in range(0, len(docs), self.batch_size):
            batch_docs = docs[i : i + self.batch_size]
            inputs = self._prepare_batch(query, batch_docs)
            
            outputs = self.model(**inputs)
            batch_scores = torch.sigmoid(outputs.logits.squeeze()).cpu().tolist()
            scores.extend(batch_scores)

        # Sort and return top-k
        ranked = sorted(zip(docs, scores), key=lambda x: x[1], reverse=True)
        return ranked[:top_k]

# ✅ Quick test
if __name__ == "__main__":
    reranker = CrossEncoderReranker(device="cuda")  # or "cpu"

    query = "How to treat type 2 diabetes with lifestyle changes?"
    candidates = [
        "Metformin is the first-line drug for type 2 diabetes.",
        "Diet modification, regular exercise, and weight loss are cornerstone non-pharmacologic therapies.",
        "Insulin pumps deliver rapid-acting insulin continuously.",
        "SGLT2 inhibitors reduce cardiovascular risk in diabetic patients.",
        "Bariatric surgery is indicated for BMI >35 with comorbidities.",
    ]

    results = reranker.rerank(query, candidates, top_k=3)
    print("Reranked Results:")
    for doc, score in results:
        print(f"[{score:.3f}] {doc}")
```

> ✅ **运行验证**：预期输出中第 2 条（lifestyle changes）应获最高分（>0.9），远超其他药物/器械相关条目。

### 4.1 架构选型：云原生 RAG 中的重排序部署模式

| 公司 | 方案 | 关键设计 | 原因 |
|------|------|-----------|------|
| **Cohere** | 自研 `rerank-3`（Bi-Encoder + Interaction Head） | 文档 embedding 预计算 + query-time interaction MLP | 保证 sub-100ms P99 延迟；支持亿级文档实时 rerank |
| **You.com** | `BGE-reranker-large` + Triton Inference Server | Dynamic Batching + FP16 + TensorRT-LLM 编译 | 吞吐提升 3.2×，A10G 单卡支撑 120 QPS |
| **LangChain Enterprise** | 插件化 reranker pipeline：支持 `Cohere` / `Jina` / `Custom HF` | 统一抽象 `BaseReranker` interface | 客户可按 cost/latency/accuracy 自由切换供应商 |
| **蚂蚁集团（AntRAG）** | 混合策略：`query length < 20 tokens → use Bi-Encoder; else → Cross-Encoder` | Query-aware routing | 平衡短 query（如“余额”）的低延迟与长 query（如“2023年杭州社保缴费基数调整通知原文”）的高精度 |

### 4.2 关键工程实践
- **缓存策略**：对高频 query（如客服 FAQ）的 rerank 结果做 Redis TTL=1h 缓存，命中率可达 35%+；
- **降级机制**：当 reranker 服务异常时，自动 fallback 到向量相似度排序（配置开关 + Prometheus 告警）；
- **A/B 测试框架**：在 Langfuse / PostHog 中埋点 `rerank_score_mean`, `llm_answer_correctness`，量化收益；
- **冷启动方案**：新业务上线初期，用 `BM25 + embedding ensemble` 作为 reranker 替代，待收集 500+ 人工标注样本后再微调。

## 5. 常见面试问题与参考答案

### Q1：Cross-Encoder 为什么比 Bi-Encoder 精度高？请从模型结构和训练目标解释。
**答**：  
- **结构差异**：Cross-Encoder 将 query 和 doc 拼接为单序列输入 Transformer，所有 layer 的 attention 可跨 query/doc token 交互；Bi-Encoder 分别编码 query/doc 得两个向量，仅用点积/MLP 计算相似度，无 token 级交互。  
- **训练目标差异**：Cross-Encoder 在 MS-MARCO 上用 pointwise ranking loss（预测二分类相关性），直接优化排序目标；Bi-Encoder 用 contrastive loss（拉近正样本、推开负样本），优化的是 embedding 空间距离，与下游排序存在目标不一致（objective mismatch）。

### Q2：重排序会引入多少延迟？如何压测和优化？
**答**：  
- 典型延迟：A10G 单卡，batch=16，avg 15ms/doc → 100 docs 需 ~100ms。压测用 `locust` 模拟并发 rerank 请求，监控 GPU util / VRAM / p99 latency。  
- 优化手段：① TensorRT-LLM 编译（-35% latency）；② FlashAttention-2（-20%）；③ 减少 max_length（512→384，牺牲少量长文档精度）；④ CPU offload 非活跃 layers（适用于大模型 reranker）。

### Q3：能否对重排序结果做进一步过滤（如去重、时效性加权）？
**答**：  
可以，且强烈推荐。典型组合策略：  
- **去重**：用 SimHash 或 MinHash 对 reranked docs 的文本哈希，移除 >0.95 相似度重复项；  
- **时效性**：若 doc 有 `publish_date` 字段，将 `1/(1+days_since_now)` 作为乘性因子，与 rerank score 相乘；  
- **权威性**：对来源域名（如 `who.int`, `cdc.gov`）赋予固定 boost（+0.1）。

### Q4：重排序模型需要微调吗？什么场景下必须微调？
**答**：  
- **通用场景（如客服、知识库）**：直接用 `bge-reranker-base` 零样本效果已很好，无需微调；  
- **必须微调场景**：① 领域术语严重 mismatch（如金融“票交所” vs 通用语料）；② 业务定义“相关性”特殊（如法律场景要求“法条援引准确率”而非语义相似）；③ 有高质量人工标注数据（>2k query-doc pairs）。微调用 `Trainer` + `MultipleNegativesRankingLoss`。

### Q5：重排序和 RAG 中的“查询扩展（Query Expansion）”是什么关系？
**答**：  
二者正交互补：  
- **Query Expansion**（如 HyDE）：在检索前改写 query（“糖尿病饮食” → “低GI食物 控制血糖 食谱”），提升初检召回率；  
- **Reranking**：在检索后精修排序，提升准确率；  
- **最佳实践**：先用 HyDE 扩展 query 检索 → 得到 200 候选 → rerank → top-5。二者叠加可提升 MRR@5 达 22%（BEIR 实验）。

## 6. 优缺点对比

| 方案 | 精度（MS-MARCO MRR@10） | 延迟（per doc, A10G） | 显存占用 | 是否支持 doc embedding 缓存 | 是否需微调 | 适用场景 |
|------|--------------------------|-------------------------|------------|------------------------------|--------------|------------|
| **BM25** | 0.182 | <0.1 ms | Negligible | ✅ | ❌ | 基线/冷启动 |
| **Embedding Cosine** | 0.295 | 0.3 ms | Low | ✅ | ⚠️（领域适配） | 高吞吐初检 |
| **BGE-reranker-base** | **0.386** | 15 ms | High (2.4GB) | ❌ | ❌ | 通用高精度 |
| **Cohere-rerank-v3** | 0.372 | 8 ms | Medium | ✅ | ❌ | 云服务集成 |
| **LLM-as-reranker (Qwen2-7B)** | 0.351 | 120 ms | Very High | ❌ | ❌ | 零样本探索 |

> 📊 数据来源：BEIR v1.0.3 + MS-MARCO Dev (2024.06)；测试环境：A10G, FP16, batch=16。

## 7. 与其他技术的关系

| 技术 | 与重排序关系 | 协同方式 |
|------|----------------|------------|
| **HyDE（Hypothetical Document Embeddings）** | 前置增强 | HyDE 生成假设文档 → 用其 embedding 检索 → rerank 原始 docs |
| **Self-RAG / Active-RAG** | 动态决策 | Agent 判断当前 step 是否需 rerank（如“答案置信度<0.7”触发） |
| **ColBERTv2** | 替代方案 | ColBERT 用 token-level matching + late interaction，精度接近 Cross-Encoder，但支持 doc embedding 缓存，延迟更低 |
| **DSPy / dspy.Reward** | 编程接口 | 将 reranker 封装为 `dspy.Reward`，参与 LM 程序自动优化（如 `dspy.teleprompt.RAGOptimizer`） |

> 💡 **趋势**：重排序正从“固定模块”演进为“可编程组件” —— 通过 DSPy、LangGraph 等框架，实现基于反馈的动态 rerank 策略调度。

## 8. 踩坑经验与注意事项

### ❌ 常见错误
1. **忽略 tokenizer 差异**：直接用 `bert-base-uncased` tokenizer 处理 `bge-reranker`，导致 `<s>` 未识别 → 全部 score=0.5；  
   ✅ 正确：`AutoTokenizer.from_pretrained("BAAI/bge-reranker-base")`。

2. **batch_size 设置过大**：在 24GB GPU 上设 batch=64 → OOM；未启用梯度检查点（`model.gradient_checkpointing_enable()`）；  
   ✅ 正确：`batch_size=16` + `fp16=True` + `device_map="auto"`。

3. **未处理长文档截断**：原始 doc 2000 字符 → tokenizer 强制截断至 512 → 关键信息丢失；  
   ✅ 正确：预处理时用 `nltk.sent_tokenize` 分句，rerank 时取 top-3 相关句子拼接。

4. **混淆 score 含义**：误将 logits 当作概率（未 sigmoid）；或与 embedding cosine score 直接比较（量纲不同）；  
   ✅ 正确：`score = torch.sigmoid(logits).item()`，且 rerank score 仅用于内部排序，不暴露给下游。

5. **线上未监控 score 分布**：某天 reranker 模型退化，所有 score 聚集在 [0.49, 0.51] → 无人发现；  
   ✅ 正确：Prometheus 指标 `reranker_score_p99` + Grafana 告警（p99 < 0.3 → 触发模型回滚）。
