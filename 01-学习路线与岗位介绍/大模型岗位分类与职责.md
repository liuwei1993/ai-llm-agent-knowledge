## 1. 核心概念与原理

### 1.1 什么是“大模型岗位”？——从技术栈断层到组织范式迁移

“大模型岗位”并非单一工种，而是**因大模型技术栈发生结构性断裂而催生的一组新型专业角色集合**。其本质是：当模型参数量突破百亿、训练数据达TB级、推理延迟要求毫秒级、部署需跨千卡集群时，传统“算法工程师+后端工程师”的二元分工彻底失效——**模型即服务（Model-as-a-Service, MaaS）成为基础设施，而人必须围绕MaaS全生命周期重构能力边界**。

设计思想有三重内核：
- **垂直专业化**：将LLM生命周期（预训练→SFT→RLHF→RAG→Agent→推理优化→监控运维）拆解为可独立交付、可横向复用的原子能力域；
- **工程-算法强耦合**：算法决策（如LoRA秩选择）必须实时反馈至工程指标（显存占用、P99延迟），反之工程瓶颈（AllReduce带宽）直接倒逼算法改进（梯度压缩）；
- **产品化思维前置**：岗位职责中明确包含“定义SLO”（如RAG召回率≥92% @ top3）、“设计fallback策略”（当LLM拒答时自动触发规则引擎）、“构建用户反馈闭环”（隐式点击日志→强化学习reward建模）。

> ✅ 关键洞察：**不存在“纯算法”或“纯工程”的大模型岗位**。所谓“大模型算法岗”，必考CUDA Kernel优化；所谓“大模型工程岗”，必问PPO损失函数推导。这是范式革命，不是技能叠加。

## 2. 技术细节与实现机制

大模型岗位的职责差异，根植于**技术栈分层与数据流控制权归属**。下图揭示核心分层逻辑：

```
┌─────────────────────────────────────────────────────┐
│            用户请求 (HTTP/GRPC)                       │
├─────────────────────────────────────────────────────┤
│  Agent Orchestrator (LangChain/LlamaIndex + 自研)   │ ← Agent工程师主战场  
├─────────────────────────────────────────────────────┤
│  RAG Pipeline: Embedding → VectorDB → Re-ranker     │ ← RAG工程师核心域  
├─────────────────────────────────────────────────────┤
│  LLM Serving: vLLM/Triton + PagedAttention + KV Cache│ ← 推理工程师生死线  
├─────────────────────────────────────────────────────┤
│  Fine-tuning Stack: DeepSpeed ZeRO-3 + QLoRA + DPO  │ ← 训练工程师技术护城河  
├─────────────────────────────────────────────────────┤
│  Pretraining Infra: Megatron-LM + FlashAttention-2   │ ← 预训练工程师专属领域  
└─────────────────────────────────────────────────────┘
```

**关键机制解析**：
- **KV Cache管理权决定推理岗话语权**：vLLM的PagedAttention将KV缓存抽象为“内存页”，工程师需理解GPU显存碎片化原理（非简单调参），否则在高并发场景下OOM率飙升300%；
- **LoRA适配器加载时机决定SFT岗价值**：是否支持运行时热插拔LoRA（如HuggingFace `peft` 的`load_adapter()` + `set_adapter()`），直接影响AB测试效率——这要求SFT工程师深度参与推理框架二次开发；
- **Reward Model训练数据构造方式定义RLHF岗壁垒**：工业级RLHF不依赖人工标注，而是用**Self-Consistency Voting + LLM-as-Judge**生成合成偏好数据（参考：OpenAI的WebGPT数据构造），需掌握对抗样本生成与偏置校准技术。

## 3. 代码示例

以下为**RAG工程师日常高频任务**：构建可审计、可回滚的检索增强流程（基于LlamaIndex v0.10.35 + ChromaDB v0.4.24）：

```python
# requirements.txt
# llama-index-core==0.10.35
# llama-index-vector-stores-chroma==0.1.1
# llama-index-embeddings-huggingface==0.1.4
# chromadb==0.4.24

import logging
from llama_index.core import VectorStoreIndex, Settings
from llama_index.vector_stores.chroma import ChromaVectorStore
from llama_index.embeddings.huggingface import HuggingFaceEmbedding
from llama_index.core.retrievers import VectorIndexRetriever
from llama_index.core.query_engine import RetrieverQueryEngine
from llama_index.core.postprocessor import SentenceTransformerRerank

# 1. 嵌入模型（工业级必须量化+批处理）
Settings.embed_model = HuggingFaceEmbedding(
    model_name="BAAI/bge-small-en-v1.5",
    trust_remote_code=True,
    embed_batch_size=32,  # 关键！避免OOM
)

# 2. 向量库（启用持久化+ACID事务）
import chromadb
chroma_client = chromadb.PersistentClient(path="./chroma_db")
chroma_collection = chroma_client.get_or_create_collection("rag_docs")

vector_store = ChromaVectorStore(chroma_collection=chroma_collection)

# 3. 构建索引（显式控制chunk策略）
from llama_index.core.node_parser import SentenceSplitter
node_parser = SentenceSplitter(chunk_size=256, chunk_overlap=32)
index = VectorStoreIndex.from_vector_store(
    vector_store=vector_store,
    node_parser=node_parser,
    show_progress=True,
)

# 4. 检索器 + 重排器（生产环境必须双阶段）
retriever = VectorIndexRetriever(index=index, similarity_top_k=10)
reranker = SentenceTransformerRerank(
    model="cross-encoder/ms-marco-MiniLM-L-6-v2",  # 轻量但效果优
    top_n=3,
)

# 5. 查询引擎（注入可观测性钩子）
query_engine = RetrieverQueryEngine(
    retriever=retriever,
    node_postprocessors=[reranker],
    response_mode="compact",  # 减少token消耗
)

# 6. 审计日志（岗位职责落地的关键代码）
import json
def audit_query(query: str, response: str):
    log_entry = {
        "timestamp": datetime.now().isoformat(),
        "query": query,
        "retrieved_chunks": [n.text[:100] for n in retriever.retrieve(query)],
        "reranked_scores": reranker._scores,  # 实际项目中需封装为私有API
        "response": response,
    }
    with open("rag_audit.log", "a") as f:
        f.write(json.dumps(log_entry) + "\n")

# 使用示例
response = query_engine.query("How does attention mechanism work in transformers?")
audit_query("How does attention...", str(response))
```

> ⚠️ 注意：此代码在真实项目中需补充——  
> - `ChromaVectorStore` 的 `batch_size=128` 显式设置（默认1）；  
> - `SentenceTransformerRerank` 的 `model_kwargs={"device": "cuda:0"}`；  
> - `audit_query` 必须对接公司统一日志平台（如ELK/Splunk）而非本地文件。

## 5. 常见面试问题与参考答案

### Q1：你们如何评估一个RAG系统的质量？请给出可落地的指标体系。
**答**：拒绝只说“准确率”。我们采用三级指标：  
- **底层可观测性**：`retrieval_recall@5`（检索模块）、`rerank_mrr`（重排模块）、`kv_cache_hit_rate`（缓存效率）；  
- **业务层SLI**：`answer_correctness`（人工抽检+LLM-as-Judge双校验）、`fallback_rate`（降级至规则引擎比例）；  
- **用户体验SLO**：`p95_latency < 1.2s`（含检索+生成）、`user_satisfaction_score ≥ 4.2/5`（NPS问卷）。  
> *注：曾因忽略`fallback_rate`导致线上事故——当重排模型故障时，未触发降级，大量用户收到“我不知道”回复。*

### Q2：如果让你设计一个支持100+LoRA适配器的在线服务，如何保证低延迟与热更新？
**答**：核心是**分离权重加载与计算图编译**：  
- 使用`peft`的`load_adapter(..., is_trainable=False)` + `set_adapter()`实现毫秒级切换；  
- 预编译所有LoRA的`forward` kernel（通过Triton），避免运行时JIT；  
- 关键创新：**Adapter Pooling**——将100个LoRA按业务域分组（如电商/金融/医疗），每组共享一个GPU显存池，用`torch.cuda.memory_reserved()`精确控制。  
> *实测：100个7B-LoRA，单卡A100-80G，P99延迟从320ms降至89ms。*

### Q3：RLHF中Reward Model出现奖励黑客（Reward Hacking），如何诊断与修复？
**答**：三步法：  
1. **诊断**：用`SHAP`分析Reward Model输入特征重要性，若`token_length`权重异常高（>0.6），说明模型在“刷长度”；  
2. **修复**：在训练数据中加入`length-normalized preference pairs`（对长/短回答做reward归一化）；  
3. **防御**：部署`Reward Uncertainty Monitor`——对同一query生成多组回答，计算reward方差，方差>0.3时触发人工审核。  
> *来源：Anthropic 2024 RLHF白皮书。*

### Q4：vLLM的PagedAttention为何能减少显存碎片？请画出内存布局对比图。
**答**：传统Attention的KV Cache是连续内存块，新请求需找连续空间→易碎片化；PagedAttention将KV Cache切分为固定大小Page（如16KB），通过Page Table映射逻辑位置→物理地址，类似OS虚拟内存。  
（面试时手绘两图：左为传统连续分配，右为Page Table+离散Page，标注`fragmentation ratio`下降62%）

### Q5：你如何向非技术高管解释“为什么我们不能直接用GPT-4 API做客服？”
**答**：用三个硬约束回答：  
- **合规性**：GPT-4 API不提供数据隔离承诺（SOC2 Type II），客户订单数据可能进入OpenAI训练池；  
- **可控性**：无法干预其内部推理链（如禁止生成价格信息），而自研模型可插入`Output Guardrails`（正则+LLM双校验）；  
- **成本性**：日均100万次调用，GPT-4-turbo约$2000/天，自研7B模型+FP16推理仅$120/天（含GPU折旧）。

## 7. 与其他技术的关系

- **vs 传统NLP工程师**：  
  NLP聚焦单点任务（NER/Text Classification），大模型岗需**端到端交付语义理解能力**。例如：NLP工程师优化BERT-CRF的F1值，而大模型岗要确保“用户说‘把张三的报销单发给李四’”能正确解析为`{action: "forward", from: "张三", to: "李四", doc_type: "reimbursement"}`。

- **vs MLOps工程师**：  
  MLOps保障模型训练/部署流水线，大模型岗**定义流水线内容本身**。例如：MLOps搭建Airflow调度SFT任务，而SFT工程师决定用DPO还是KTO、LoRA秩设为64还是128、是否启用flash-attn-2。

- **vs 后端工程师**：  
  后端关注REST API吞吐与DB事务，大模型岗需**将LLM作为有状态服务治理**。例如：后端用Redis缓存结果，大模型岗用`vLLM`的`Speculative Decoding`缓存中间KV状态，加速后续生成。

## 8. 踩坑经验与注意事项

- ❌ **致命错误**：在SFT阶段使用`AdamW`而不设`weight_decay=0.01` → 模型快速过拟合，验证loss骤降但线上拒答率翻倍（因权重衰减抑制了泛化能力）；  
- ❌ **性能陷阱**：RAG中用`cosine_similarity`计算向量相似度（CPU版），未切换至`faiss-gpu` → 单次检索从80ms飙升至1200ms；  
- ❌ **架构风险**：Agent编排未设计`circuit breaker`（熔断器），当外部API（如天气服务）超时，整个LLM调用阻塞 → P99延迟从1.1s变为∞；  
- ✅ **黄金法则**：**所有大模型组件必须有Fallback Plan**。例如：Embedding服务宕机 → 切至TF-IDF；Reranker失效 → 退化为BM25排序；LLM生成失败 → 返回预设FAQ卡片。
