# 轨迹评估（Trajectory Evaluation）

> **定位**：Agent 系统可观测性的核心支柱，是区别于传统 LLM 应用（单次 prompt → response）的关键评估维度。  
> **本质**：对 Agent 在完成任务过程中所生成的**完整决策链（planning → tool selection → tool execution → reasoning → synthesis）** 进行结构化、可量化、可归因的质量评估。  
> **工业共识**：在字节跳动「Lemonade」Agent 平台、阿里云「Tongyi Agent Studio」、美团「Meituan Copilot」及 Anthropic 的「Constitutional Trajectory Auditing」实践中，轨迹评估已从实验性模块升级为**SLO（Service Level Objective）强制准入项**——任何上线 Agent 必须通过 L1–L4 四层轨迹合规性门禁，否则禁止接入生产流量。

---

## 1. 核心概念与原理

### 1.1 什么是轨迹（Trajectory）？
在 Agent 系统中，**轨迹（Trajectory）** 指模型在一次任务执行中产生的**有序动作序列（Action Sequence）**，通常包含以下结构化字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `step_id` | int | 步骤序号（从 0 或 1 开始） |
| `action_type` | str | `plan`, `tool_call`, `tool_response`, `reasoning`, `final_answer` |
| `tool_name` | str (optional) | 调用工具名（如 `"search_web"`, `"get_weather"`） |
| `tool_input` | dict (optional) | 工具参数（JSON-serializable） |
| `tool_output` | any (optional) | 工具返回结果（可能为 str/dict/list） |
| `reasoning` | str (optional) | 当前步骤的思考依据（如 “用户问北京天气，需先调用 weather API”） |
| `status` | str | `success`, `failed`, `skipped`, `loop_detected` |
| `timestamp` | float | Unix timestamp（毫秒级，用于时序分析） |
| `latency_ms` | float | 本步耗时（从 action 触发到 status 更新） |
| `context_hash` | str | 基于当前 step 输入 + memory snapshot 的 SHA256，用于去重与模式聚类 |

> ✅ **关键洞察**：轨迹 ≠ 日志（log）。日志是原始、非结构化的运行记录；而轨迹是**语义增强、schema 化、面向评估建模的中间表示**。它是 Agent 的“行为 DNA”。  
> 🔍 **真实踩坑案例（字节跳动 2023 Q4）**：某电商客服 Agent 在 A/B 测试中最终答案准确率达 92%，但轨迹分析发现其 `plan_tool_consistency_score` 仅 0.37 —— 73% 的 `tool_call` 动作未被 plan 提前声明，而是靠 LLM “临场发挥”调用 `refund_api`。上线后遭遇支付网关 schema 升级（新增 `refund_reason_code` 必填字段），因无 plan 约束导致 100% 调用失败，SLA 瞬间跌至 11%。**轨迹评估提前 3 周捕获该风险，避免千万级资损。**

### 1.2 为什么需要轨迹评估？—— 从黑盒到白盒诊断
传统 LLM 评估（如 BLEU、ROUGE、BERTScore）仅看输入→输出映射，但 Agent 是**状态机 + 外部交互系统**：
- ❌ 单靠最终答案正确 ≠ Agent 可靠：可能靠运气跳过关键步骤、误用工具但凑巧返回对结果；
- ❌ 高任务成功率 ≠ 高可维护性：某路径在测试集上成功，但在新工具 schema 下立即崩溃；
- ✅ 轨迹评估提供**归因能力（Attribution）**：当失败发生时，能精准定位是 `规划错误`（Plan）、`工具误选`（Tool Selection）、`参数错误`（Tool Input）、`响应解析失败`（Tool Output Parsing）、`记忆污染`（Memory Corruption）还是 `合成偏差`（Synthesis Hallucination）。

更进一步，轨迹是**唯一可工程化定义 Agent 行为契约（Behavioral Contract）的载体**。例如：
- **可复现性保障**：给定相同 `input + system_prompt + tool_spec + memory_state`，轨迹应严格一致（排除非确定性扰动后）；
- **合规审计基础**：金融/医疗类 Agent 需满足《AI应用安全评估指南》第 5.2 条：“所有外部调用必须有前置意图声明与后置结果验证”，该条款直接映射为 `plan → tool_call → tool_response → validate` 四元组完整性校验；
- **渐进式可信构建**：通过 `trajectory entropy`（步骤分布熵）、`tool_call_diversity_index`（工具调用香农指数）、`reasoning_coherence_score`（跨步推理连贯性）等指标，量化 Agent 的“思维成熟度”。

## 2. 工业级轨迹评估体系：L1–L4 四层门禁

> ⚙️ **设计哲学**：不追求“一次性完美评估”，而构建**漏斗式防御体系**——越靠近生产环境，评估粒度越细、成本越高、覆盖越全。

| 层级 | 名称 | 触发时机 | 核心指标（示例） | 典型阈值 | 工业实现方式 |
|------|------|-----------|------------------|------------|----------------|
| **L1** | **Schema 合规性** | 请求入队前（Pre-execution） | `missing_field_rate < 0.1%`, `invalid_action_type_count == 0`, `tool_input_json_schema_valid == True` | `schema_validity ≥ 99.99%` | JSON Schema + Pydantic v2 strict mode + 自定义 `TrajectoryStepValidator` |
| **L2** | **逻辑一致性** | 执行中实时（In-flight） | `plan_tool_coverage ≥ 0.95`, `tool_response_to_call_latency_ratio ≤ 3.0`, `loop_step_count ≤ 2` | `consistency_score ≥ 0.88` | 基于有限状态机（FSM）的在线轨迹流式校验器（字节自研 `TrajGuard`） |
| **L3** | **语义鲁棒性** | 执行后离线（Post-hoc） | `reasoning_factual_alignment ≥ 0.91`（对比 tool_output 与 reasoning 文本），`tool_output_parse_success_rate ≥ 0.995`，`memory_leakage_score ≤ 0.05`（基于差分隐私敏感度检测） | `robustness_score ≥ 0.82` | 多模态评估 pipeline：LLM-as-a-judge（Claude-3.5-Sonnet）+ 规则引擎（正则/AST 解析）+ 工具响应 schema diff analyzer |
| **L4** | **业务目标对齐** | 全量回溯（Batch Audit） | `task_success_via_trajectory_path ≥ 0.94`, `avg_steps_per_success_task ≤ 5.2`, `cost_per_successful_trajectory ≤ $0.082`（含 token + tool + cache） | `business_alignment ≥ 0.90` | 基于因果图（Causal Graph）的反事实轨迹重放（Counterfactual Trajectory Replay） + 成本-效果 Pareto frontier 分析 |

> 📌 **关键实践**：  
> - **L1/L2 必须硬拦截**：违反即 `500 Internal Trajectory Error`，拒绝响应；  
> - **L3 支持灰度降级**：若 `reasoning_factual_alignment < 0.85`，自动 fallback 至 deterministic rule-based planner；  
> - **L4 为月度 SLO 报告核心**：驱动 Agent 架构迭代（如将高频 `search_web → parse_html → extract_price` 三步合并为原子工具 `get_product_price`）。

## 3. 高级设计模式与复杂场景应对

### 3.1 多智能体协同轨迹（Multi-Agent Trajectory）
当多个 Agent 协同完成任务（如「旅行规划 Agent」调用「酒店预订 Agent」+「航班比价 Agent」），轨迹不再是线性序列，而是**有向无环图（DAG）**：

```python
# 示例：DAG 轨迹片段（Pydantic v2 Model）
class TrajectoryNode(BaseModel):
    node_id: str  # e.g., "hotel_agent_20240521_001"
    parent_ids: List[str] = Field(default_factory=list)
    agent_role: str  # "coordinator", "executor_hotel", "executor_flight"
    sub_trajectory: List[TrajectoryStep]

class MultiAgentTrajectory(BaseModel):
    root_node: TrajectoryNode
    all_nodes: Dict[str, TrajectoryNode]  # topological sort key
    cross_agent_consistency_score: float  # e.g., shared context hash match rate
```

> 🔧 **挑战与解法**：  
> - **时序漂移（Temporal Drift）**：子 Agent 响应延迟导致 coordinator 等待超时 → 引入 `max_wait_ms_per_dependency` 动态阈值（基于历史 P95）；  
> - **上下文污染（Context Bleed）**：A Agent 的 memory 泄露至 B Agent → 在 DAG 边界插入 `context_isolation_layer`（SHA256 哈希校验 + 敏感字段 redaction）；  
> - **归因模糊（Attribution Ambiguity）**：最终失败无法定位根因 → 使用 **Shapley value-based trajectory credit assignment**（开源库 `shapley-traj`），量化各节点对 success/failure 的边际贡献。

### 3.2 长周期轨迹（Long-Horizon Trajectory）
针对需数小时/数天完成的任务（如「科研文献综述 Agent」持续爬取、筛选、阅读、摘要），轨迹评估面临：
- **存储爆炸**：单轨迹达 10k+ 步 → 采用 **delta-compressed trajectory storage**（只存 `reasoning` diff + `tool_output` hash）；
- **状态衰减**：早期 plan 被后续步骤覆盖 → 引入 **plan versioning**：每个 `plan` 步骤带 `plan_version: int` 与 `valid_until_step_id: int`；
- **人类干预点（Human-in-the-loop）**：用户中途修正 → 新增 `human_intervention_event` 类型 step，强制触发 `plan_revalidation_checkpoint`。

> 🌐 **美团「Meituan Copilot」实战**：外卖调度 Agent 处理“跨城生鲜配送”任务（平均 37.2 步），通过长周期轨迹分析发现：`step_id=18` 的 `weather_forecast` 工具调用结果被 `step_id=29` 的 `traffic_prediction` 工具覆盖，导致冷链温控策略失效。上线 `cross-step dependency graph validator` 后，该类故障下降 91.3%。

### 3.3 对抗性轨迹鲁棒性（Adversarial Trajectory Robustness）
恶意用户可能构造诱导性输入，触发高成本/低价值轨迹（如反复调用 `search_web` 生成冗余步骤）。评估需覆盖：
- **成本异常检测**：`token_cost_per_step > 3× median` 且 `tool_call_count > 5` → 触发 `budget_guard` 中断；
- **语义冗余识别**：使用 Sentence-BERT 计算连续 `reasoning` 步骤的余弦相似度，`similarity > 0.82` 持续 3 步 → 标记 `reasoning_loop_risk`；
- **工具滥用模式挖掘**：基于 `tool_name + tool_input.keys()` 的频繁项集（Frequent Itemset Mining），识别 `{"search_web": ["query"], "parse_html": ["url"]}` 组合高频出现 → 自动聚合为新工具 `search_and_parse`。

> 🛡️ **Anthropic 实践**：在其 Constitutional Trajectory Auditing 中，将 `adversarial_trajectory_robustness_score` 定义为：  
> $$ \text{ATR} = 1 - \frac{\text{# of adversarial trajectories causing cost > \$0.5 or latency > 8s}}{\text{# of total adversarial probes}} $$  
> 要求所有生产 Agent 的 ATR ≥ 0.9995（P99.9）。

## 4. 性能调优 Benchmark：轨迹评估开销实测（Python 3.11 + Pydantic v2.6）

| 评估层级 | 方法 | 平均耗时（per trajectory） | 内存占用 | 支持并发 | 生产部署方式 |
|----------|------|-----------------------------|------------|-------------|----------------|
| **L1 Schema Check** | Pydantic `model_validate` + custom validators | 0.87 ms | 124 KB | 10k QPS | 同步嵌入 Agent runtime（`pre_run_hook`） |
| **L2 Logic FSM** | `trajector-guard`（Rust 编译 PyO3 binding） | 2.3 ms | 89 KB | 22k QPS | Sidecar 进程（gRPC stream） |
| **L3 Semantic Judge** | Claude-3.5-Sonnet API（batched） + local regex engine | 1.8 s | 3.2 MB | 120 QPS | 异步 worker pool（Celery + Redis） |
| **L4 Causal Replay** | `do-calculus` + `causalml` + `ray` 分布式重放 | 42.7 s | 1.1 GB | 8 QPS | Nightly batch job（Airflow DAG） |

> 💡 **关键优化经验**：  
> - **L1/L2 必须零 GC 延迟**：禁用 Python GC，使用 `__slots__` + `array.array` 存储 step 列表；  
> - **L3 的 LLM Judge 成本可控化**：对 `reasoning_factual_alignment`，仅对 `tool_output` 非空且 `reasoning` 长度 > 50 字符的 step 调用 LLM，其余用规则引擎（覆盖率 83.7%，准确率 96.2%）；  
> - **L4 的因果图缓存**：预编译常见任务类型（如“订机票”）的 causal skeleton，重放时仅注入 runtime 数据，提速 17×。

## 5. 面试深度追问连环题（附参考答案）

**Q1**：如果一个轨迹中 `plan` 步骤声明将调用 `get_stock_price(symbol="AAPL")`，但实际 `tool_call` 是 `get_stock_price(symbol="TSLA")`，这属于哪类错误？如何自动化检测？  
✅ **答**：属 **Tool Selection Error**（非 Tool Input Error）。检测需两步：① 提取 `plan` 中所有工具调用声明（正则 `/get_stock_price\([^)]*symbol=["']([^"']+)["'][^)]*\)/g`）；② 与实际 `tool_call` 的 `tool_input.symbol` 比对。工业方案：字节 `PlanParser` 使用 AST 解析（支持嵌套 plan），准确率 99.98%。

**Q2**：如何证明某个 Agent 的 `reasoning` 步骤不是“事后编造”（post-hoc rationalization），而是真实驱动了下一步动作？  
✅ **答**：实施 **Interventional Reasoning Validation**：对 `reasoning` 文本做最小扰动（如替换实体、否定逻辑），重放轨迹，观察 `next_action_type` 是否改变。若 95% 扰动导致 action 变更，则视为 causal reasoning。OpenAI 在 `o1-preview` 中采用此法，要求 `intervention_sensitivity ≥ 0.92`。

**Q3**：轨迹评估发现某 Agent 的 `tool_response` 字段常为空字符串，但 `status=success`。根本原因可能是什么？如何根治？  
✅ **答**：典型原因：① 工具 SDK 返回 `None` 未转空字符串；② Agent runtime 的 `tool_output_parser` 将空响应误判为成功。根治：在 L1 加入 `tool_output_nonempty_on_success` 校验，并强制所有工具实现 `output_schema`（JSON Schema 定义），空响应触发 `status=failed` + `error_code=TOOL_OUTPUT_EMPTY`。

**Q4**：当轨迹长度超过 1000 步时，`context_hash` 计算开销剧增，如何保持实时性？  
✅ **答**：采用 **incremental Merkle tree hash**：每步计算 `H(step_id || action_type || H(prev_context_hash) || tool_input_hash)`，O(1) 更新。阿里云 Tongyi Agent Studio 使用此法，10k 步轨迹哈希耗时稳定在 3.2 ms。

**Q5**：能否用轨迹评估替代传统 A/B 测试？为什么？  
✅ **答**：**不能替代，但可大幅压缩 A/B 周期**。轨迹评估揭示 *why*，A/B 测试回答 *whether*。最佳实践：用轨迹评估快速淘汰 80% 明显缺陷版本（L1–L3 门禁），仅对通过者进行小流量 A/B（<5%），聚焦 L4 业务指标。美团实测将平均发布周期从 14 天缩短至 3.2 天。
